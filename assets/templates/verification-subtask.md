# 子任务 / 子 agent 核查模板（上下文隔离）

> 用法：每条待验声明开一个**独立的**子任务/子 agent，把下面内容填进去发出去。
> 铁律：**禁止把初稿内容写进背景段**。一旦模型看到自己的草稿，核查就退化成"为自己辩护"
> （CoVe, arXiv 2309.11495：factored 隔离明显优于 joint）。

---

## 模板 A · 单条声明核查

```text
【独立核查任务 · 禁止参考主会话结论】

背景（最小必要，不含任何结论性表述）：
  {只写需要定位的材料范围，例如："本项目是一个 Kotlin + Compose 的 Android 应用，代码在 app/ 下"}

核查目标（单条原子声明）：
  {声明文本，或三元组 (主体, 关系, 客体)}

你的任务：
  1. 只针对这一个目标收集证据：读文件 / 跑命令 / 查官方文档 / 检索
  2. 优先设计反证方向：有什么证据能推翻这条声明？
  3. 不要读取主会话的草稿、结论或其他核查任务的中间结果

输出（严格按此结构）：
  - 结论：supported | contradicted | unverified
  - 证据：原文摘录（逐字，不要改写）
  - 来源：文件路径#行号 / URL / 命令（哪个命令、什么输出）
  - 反证：你查过哪些可能推翻它的方向，结果如何
  - 置信度：高 / 中 / 低 / 无
  - 替代可能：如果这条不成立，最可能的正确答案是什么

硬要求：
  - 工具失败 / 找不到 / 检索为空 → 输出 unverified，**不要猜测**
  - 没有证据就不要写 supported
  - 给出 unverified 比给一个不确定的答案有价值
```

## 模板 B · 大项目现状核查（防记忆漂移）

```text
【当前现状核查 · 只信本次实际读到的内容】

项目根目录：{root}
待核实项：{例如 "DI 框架用的是什么" / "Chat 模块是否已完成"}

步骤：
  1. 用 rg / grep / ls 定位真实证据（不要凭训练记忆，也不要凭"以前见过"）
  2. 贴出真实的命令与输出
  3. 与账本 .touchstone/ledger.json 中的条目比对；不一致时**以代码为准**

输出：
  - 实际观测到的内容（含文件路径 + 行号）
  - 与账本是否一致；不一致则说明哪边过期
  - 标签：observed（单次观测）/ contradicted（账本与现实冲突）
  - 观测时间
```

## 模板 C · 引用/实体存在性核查（微软 refchecker 思路）

```text
【窄面核查：这些项是否真实存在】

待查清单：
  - URL: {...}
  - DOI: {...}
  - 论文：标题 + 作者 + 年份
  - 实体/产品/API：{...}
  - 文件路径：{...}
  - 版本号：{...}

要求：
  1. 每一项**实际去查**：发请求 / 解析 DOI / ls 文件 / 查 registry
  2. 查不到 = 不成立，不是"大概成立"
  3. 网络失败记为 unverified，不记为通过

输出：
  - 逐项：PASS / FAIL / UNVERIFIED + 证据
  - 汇总："通过数/总数"
  - FAIL 项对应的声明必须删除或替换
```

## 派发要点

| 环节 | 要点 |
|---|---|
| 一条一发 | 不要把多条声明塞进一个子任务（会互相锚定） |
| 背景要穷 | 背景段只给定位信息，不给结论 |
| 回收要验 | 子 agent 的结论默认 `hearsay`，独立验证后才升级 |
| 冲突要报 | 多个子 agent 结论冲突 → 不一致本身就是信号，走 L2 升级 |
