# 04 · M4 核查工作流（八步）

> 骨架：FacTool 五段式（GAIR-NLP, Apache-2.0）
> 关键改进：CoVe 的 factored 验证（arXiv 2309.11495）+ verify-gate 的先证伪

---

## 完整流程

```
[门] 入场门       四问 G1–G4 全"是" → 小任务，不进本流程，直接答（见 SKILL.md）
[0] 判上下文     Zero / Noisy / Accurate        → 决定用哪种手段（见 02）
[1] 起草         正常产出，允许不完美
[2] 原子化       拆成原子声明 / 三元组
[3] 硬核查       可判定项先真查（见 03 + hardcheck.py）
[4] 规划验证     每条生成"能证伪它"的问题，优先反证方向
[5] 独立作答     子任务隔离上下文 ← 有效性关键
[6] 打分贴标签   confirmed/observed/assumed/hearsay/unknown + 置信度 + 反例
[7] 修订留痕     contradicted 改或删，unverified 降格或删并留 []
[8] 执行同闸     "做完了"也要验证
[闸] claim_lint  交付前跑 scripts/claim_lint.py，非零退出码不许交付
```

## Step 2 · 原子化

**为什么要拆**：CoVe 论文的"筒仓知识悖论"——长文生成中某事实的准确率只有 ~17%，但把同一事实拆成独立提问时准确率升到 ~70%。**拆分是白捡的准确率。**

### 拆法

- 一句一拆，**一条声明只包含一个可验证的事实**
- 结构化主张用三元组 `(主体, 关系, 客体)`
- 观点、建议、推断单独标类型，不混进事实核查

### 示例

```
原文：
"Hyper-RAG 是清华大学高跃团队 2026 年发表在 Nature Communications 的工作，
相比 GraphRAG 降低了 48.5% 的幻觉。"

→
C1 (Hyper-RAG, 提出方, 清华大学高跃团队)      事实  需外验
C2 (Hyper-RAG, 发表于, Nature Communications) 事实  需外验
C3 (该论文, 发表年份, 2026)                   事实  需外验
C4 (Hyper-RAG, 相对基线, GraphRAG)            事实  需外验
C5 (Hyper-RAG, 幻觉降低幅度, 48.5%)           事实  需外验  ← 数字必须回溯一手
```

**三元组粒度**（RefChecker）的理由：比段落/句子细，且**可以向上聚合**——需要粗粒度时随时 roll up，反过来不行。

## Step 4 · 验证问题设计

**优先设计能证伪的问题，不是找支持。**

| 声明 | ❌ 弱验证问题 | ✅ 强验证问题 |
|---|---|---|
| "X 是 MIT 教授" | "X 在哪工作？" | "X 目前任职于哪个机构？有没有证据表明他不在 MIT？" |
| "该 API 支持批量调用" | "这个 API 能做什么？" | "官方文档里 batch 参数的确切名称和取值上限是什么？" |
| "2023 年发表" | "什么时候发表的？" | "这篇论文的正式发表年份是？有没有预印发在 2022 的情况？" |
| "项目用 Hilt 做 DI" | "项目用了什么 DI？" | "build.gradle.kts 里有哪些 DI 相关依赖？有没有 Koin 的痕迹？" |

## Step 5 · 独立作答（最关键的一步）

### 子任务 prompt 模板

```
【核查任务】
请独立回答下面的问题。

问题：{验证问题}

要求：
1. 只回答这一个问题，不要参考其他内容
2. 优先使用检索/工具获取证据，不要凭记忆
3. 给出证据来源（文档名 + 章节，或 URL）
4. 如果查不到，明确回答"未找到可靠来源"——这比给一个不确定的答案有价值

输出：
- 结论：
- 证据：
- 来源：
- 置信度（高/中/低）：
```

### 子 agent（大项目）模板

```
【独立核查 · 禁止参考主会话】
背景：{最小必要背景，不含任何结论性表述，不含初稿}
核查目标：{单个原子声明}
任务：
  1. 只针对该目标收集证据（读文件 / 跑命令 / 检索）
  2. 输出：结论(supported/contradicted/unverified) + 证据原文摘录 + 来源路径
  3. 禁止读取主会话的草稿或结论
  4. 工具失败 / 找不到 → 输出 unverified，不要猜测
```

### 三条硬约束

1. **禁止把初稿内容放进这个 prompt。** 模型一旦看到初稿，就会被锚定，核查退化成"为自己辩护"。
2. **每个验证问题一个独立子任务**，不要批量塞在一个 prompt 里。
3. **工具失败 / 检索为空 → 记为 `unverified`**，绝不当作通过。

> 这是 CoVe 论文的核心发现：**factored（隔离）明显优于 joint（一起给）**。省这一步，整套流程的价值归零。

## Step 7 · 修订留痕

| 判定 | 动作 |
|---|---|
| `supported` | 保留，标 `confirmed` + 来源 |
| `contradicted` | 修正为正确版本；无法修正就删除，原位留 `[]` |
| `unverified` | 降格为 `assumed`（文中必须带标签）或直接删除留 `[]` |

**留痕要求**：核查日志要写清楚——哪条查了、源是什么、哪条没查到、为什么删。没有记录的 `confirmed` 标签是假徽章。

---

## Step 8 · 执行声明同闸

**"任务完成"必须通过同一道闸。**

| 声称 | 需要的证据 |
|---|---|
| 文件已创建 | `ls -la` 输出 或 `stat` |
| 测试通过 | 测试命令完整输出（含 pass 数），不是"应该过了" |
| Bug 已修复 | 原始症状复现 → 修复后不复现 |
| 已发送请求 | 工具返回值 / 回执 |
| 服务已启动 | 实际 curl / 健康检查 |
| 编译通过 | 构建命令完整输出（含 BUILD SUCCESSFUL） |

**反面清单**：
- "我很有把握" → 信心不是证据
- "改动很小，不可能出错" → 小改动天天搞崩构建
- "子 agent 说做完了" → 它的报告也是声明，独立验证
- "CI 会兜住" → CI 是安全网，不是验证
- 用户说"太棒了" → 那是感官数据，不是验证

## 闸门 · claim_lint

交付前最后一步：

```bash
python3 scripts/claim_lint.py --input claims.json --min-level L1
```

它校验的不是格式，是**逻辑一致性**：
- `confirmed` 是否真的有 ≥2 个独立源 + `counter_evidence_checked: true`
- `observed` 是否带了观测时间
- 置信度 < 0.6 是否附了 `alternative`
- 是否存在无源却以事实口吻呈现的声明
- `risk_level = L2` 是否走了人工闸门

**闸门不放行 = 不许交付。** 这是把"请你仔细检查"换成结构性约束的关键一步。
