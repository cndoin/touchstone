# 20 · 工具调用模式：链不许断，中途不许忘

> **一句话：工具调用的幻觉大部分不在"单次调用对不对"，而在"这条链还记不记得自己在干什么"。**
>
> 单次调用的真伪（有没有这个工具、参数对不对）已有闸门覆盖；
> 真正的新盲区是**调用链本身**——顺序、闭环、幂等、前置、目标漂移。
> 这一层的幻觉有个共同形态：**每一步单看都对，连起来看是错的**，
> 所以逐条校验工具名永远抓不到，必须把调用当"链"来核。

---

## 0. 什么时候进工具调用模式

触发条件（满足任一条即进入）：

- 一次任务里**同一个目标上连续做了 3 次以上**工具调用（读→改→验→发）
- 涉及**不可逆副作用**：推送、发布、发送、删除、merge、部署
- 出现**失败与重试**：某个调用 fail 之后又调了它
- 任务**中途换过目标**（用户改需求、发现新问题、拆分子任务）
- 上下文**被截断过**（compact / 长任务 / 多会话接力 / 子 agent 汇总后继续）
- 你正准备说"已完成""全部就绪""都推送了"

不触发：单次问答、单文件一次改完、没有副作用的纯查询。

**"忘了在干什么"为什么危险**：它不会立刻报错。链断了、目标漂了、重复推送了，
每一步的输出看起来都正常，**错误在汇总层才显形**——往往已经是不可逆事故
（重复发的通知收不回来、推错分支的 commit 删不干净）。

---

## 1. 工具调用幻觉长什么样：六个层，各管各的

| 层 | 症状 | 本质 | 谁来治 |
|---|---|---|---|
| **① 调用真伪层** | 编造工具名 / 参数名 / 子命令 | 这个工具根本不存在 | **已有**：`dep_guard.py`（import/包名）、各技能白名单 lint |
| **② 链状态层** | seq 跳号；`started` 没下文；调用开了头就丢 | 链本身不完整 | **`tool_guard.py --only order,closure`** |
| **③ 副作用与幂等层** | 重复推送 / 重复发送 / 重复删除 | 同一不可逆操作做了两次 | **`tool_guard.py --only duplicate,retry`** |
| **④ 前置依赖层** | 没读就改、没存就发、没查就删 | 凭印象操作 | **`tool_guard.py --only prereq`** |
| **⑤ 目标漂移层** | 中途换 goal / 改计划步数不吭声 | 「忘了原来在干什么」 | **`tool_guard.py --only plan`** |
| **⑥ 结果误读层** | `exit_code=1` 却记成 ok；报错被当成功 | 工具成功 ≠ 做对了 | **`tool_guard.py --only result`** |

**用错层的代价**：
- 给第 ⑤ 层查工具名不管用——工具都是真实存在的，**错的是链的意图**；
- 给第 ② 层讲道理不管用——"记得收尾"写一百遍也没用，**要机器查**；
- 第 ① 层**已有专门工具**，别在本章重造（见第 5 节分工表）。

## 2. 核心：「调到一半忘了前面在干什么」的可观测症状

这是本模式存在的主因。它主观上无法自察（忘了就是忘了），
所以只能抓**客观症状**——以下 8 条全部可由调用记录判定，一条都不靠自觉：

| # | 症状 | 记录上的形态 | 闸门条款 |
|---|---|---|---|
| 1 | 调用链断裂 | `seq` 跳号 / 重复 / 乱序 | `order` |
| 2 | 开了头没下文 | `status=started` 之后无终态 | `closure` |
| 3 | 同一操作做两遍 | 非幂等工具同 target 多次 `ok` | `duplicate` |
| 4 | 撞墙式重试 | 同参数 fail 连续 ≥3 次不换策略 | `retry` |
| 5 | 凭印象改文件 | 写/改前无同 target 的读取 | `prereq` |
| 6 | 目标悄悄漂移 | `goal` 中途改变且无 `rescope` | `plan` |
| 7 | 计划被悄悄改写 | `step` 总数中途变且无 `rescope` | `plan` |
| 8 | 把失败当成功 | `status=ok` 但 `exit_code≠0` 或带 `error` | `result` |

**症状 1–2 是「链忘了」，3–4 是「手忘了」，5 是「内容忘了」，
6–7 是「目标忘了」，8 是「结果忘了」。** 五个"忘了"各有各的记录形态，
这就是为什么必须先有记录再谈核查（见第 3 节）。

⚠️ **`started` 是唯一的非终态。** `ok / fail / skipped / aborted` 都代表"这次调用结束了"；
只有 `started` 表示"开了头"。所以"没下文"的判定是精确的，不靠猜。

## 3. 记录契约：`assets/tool-trace-schema.json`

**先有记录，才有核查。** 链的核查对象是调用记录（trace），不是事后回忆——
事后回忆本身就是"忘了"之后补写的，天然不可信。

一条调用记录的最小形态：

```json
{"seq": 2, "tool": "edit", "target": "scripts/pipeline.py", "status": "ok",
 "goal": "给 pipeline 加第 5 步并验证", "step": "2/5", "consumes": [1]}
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `seq` | ✅ | 调用序号，从 1 起连续递增 |
| `tool` | ✅ | 工具名（小写比对） |
| `status` | ✅ | `ok` / `fail` / `skipped` / `started` / `aborted` |
| `target` | — | 操作对象（文件路径 / 分支 / 服务名） |
| `goal` | — | 本次任务目标；中途不许悄悄变 |
| `step` | — | 形如 `2/5` 的进度；总步数不许悄悄变 |
| `exit_code` / `error` | — | 工具真实回执；与 `status` 必须一致 |
| `consumes` | — | 本次调用依据了哪几条（通常是前置读取的 `seq`） |

**三种输入形态都收**：整体 JSON（带 `trace` 数组，可带顶层 `partial`/`goal`）、
纯 JSON 数组、JSONL（每行一条）。解析失败按**失败**计，不是"没查过"。

## 4. 可执行闸门：`tool_guard.py`（八个检查器）

```bash
PY=python3          # Windows 用 python

# 核查一份调用链记录
python3 scripts/tool_guard.py --file trace.json

# 多份记录一起核（多会话 / 多子 agent 各记各的，最后合并核查）
python3 scripts/tool_guard.py --file a.json --file b.json

# 只跑指定检查器
python3 scripts/tool_guard.py --file trace.json --only plan,closure

# 调重试阈值（默认 3）
python3 scripts/tool_guard.py --file trace.json --max-retry 2

# 离线 + 严格模式（unverified 一律按失败计）
python3 scripts/tool_guard.py --file trace.json --offline --strict
```

**八检查器一览**（与第 1 节的层一一对应）：

| 检查器 | 查什么 | 典型拦截 |
|---|---|---|
| `schema` | 记录结构与枚举值 | `status` 拼错、缺 `seq` |
| `order` | seq 递增 / 无重复 / 无跳号 | 漏记了一次调用 |
| `closure` | `started` 之后没有终态 | 调用开了头就丢 |
| `duplicate` | 非幂等操作同 target 重复 `ok` | 重复推送 |
| `retry` | 同参数连续失败不换策略 | 撞墙式重试 |
| `prereq` | 改前未读 / 发前未存 | 凭印象改 |
| `plan` | `goal` / 步骤总数中途变 | 目标漂移 |
| `result` | `ok` 却 `exit_code≠0` 或带 `error` | 失败被记成成功 |

**每文件 × 每检查器各出一条结论**（无异常也出 `PASS`），
所以 `合计 = pass + fail + unverified` 可以逐条核对。
**"没把话说完"本身就是假信号**：干净的链也要明说"查过了，N 条调用无异常"，
而不是沉默——沉默与"没查"在输出上无法区分。

退出码：`0` 通过 / `1` 有失败 / `2` 未验证 / `3` 用法错误（与全套件一致）。

## 5. 与既有闸门的分工（重要：不重复造）

| 闸门 | 管什么 | 判定对象 | 与本模式的关系 |
|---|---|---|---|
| `claim_lint.py` | **声明层**：输出契约，每条结论有无证据标签 | 最终文本 | 不看过程。它管"你说了什么"，本模式管"你做了什么" |
| `hardcheck.py` | **事实层**：URL / DOI / 文件 / 命令 / 版本真伪 | 单条事实 | 不看顺序。它管"这条证据是不是真的"，本模式管"证据链接不接得上" |
| `dep_guard.py` | **依赖层**：import / 包名 / 符号真伪 | 代码文本 | 管第 ① 层（调用真伪），本模式管第 ②–⑥ 层 |
| `ledger.py` | **决策层**：架构决策与约定的漂移 | 项目账本 | 管"项目层面有没有忘"，本模式管"一次任务内有没有忘" |
| `bio_guard.py` / `mathcheck` | **领域层**：生物实体 / 数值执行记录 | 领域声明 | 与本模式正交，各自独立 |
| **`tool_guard.py`** | **过程层**：调用链的完整性与意图一致 | 调用记录 | 本章新增 |

**一句话分工**：`claim_lint` 管"说的"，`hardcheck` 管"引的"，
`dep_guard` 管"用的工具真不真"，`tool_guard` 管"做的过程接不接得上"。
四者互不替代，交付前都跑（`pipeline.py` 串起来）。

## 6. 免责字段：举证责任在记录方

有些"重复"是合法的。判据**不在工具名**，而在记录里显式举证：

| 字段 | 免什么责 | 为什么要有 |
|---|---|---|
| `idempotent: true` | 幂等重放不算重复副作用 | 重发一条幂等请求是安全的 |
| `creates: true` | 新建资源不需要先读 | 建新文件本来就无从读起 |
| `rescope: true` | 目标 / 计划中途改变是合法的 | 换目标本身没错，**瞒着换**才是"忘了" |
| `retry_of: N` | 对第 N 条失败调用的补救 | 失败后补一次是补救，不是重复副作用 |

**为什么不做"工具名自动放行"**：`write` 既能建新也能覆盖。
按名字放行会同时漏掉"覆盖了旧文件却没读过"这个真问题——
所以免责必须由记录方**显式声明**，机器只认字段不认名字。
误报太多的闸门会被绕过，等于没有闸门；漏报太宽的闸门同理。

## 7. 最小执行清单（照抄即可）

1. **起任务时先定 goal**，写进 trace 顶层；步骤多于 3 步就标 `step: i/N`
2. **每做完一次调用就记一行**（seq / tool / target / status / 回执），
   不要攒到最后补——补写的就是回忆，而"忘了"恰恰发生在回忆里
3. 失败重试时**改点什么**（参数 / 路径 / 策略），并在记录里留 `retry_of`
4. 换目标 / 改计划 → 立刻在记录里标 `rescope: true`，**不要悄悄换**
5. 交付前跑：
   ```bash
   python3 scripts/tool_guard.py --file trace.json --offline --strict
   ```
6. `--strict` 非零退出 = 不许说"已完成"。先修记录或补做，而不是改措辞绕过去

## 8. 边界（诚实说明）

- **只核记录，不核现实。** 记录说 `read: 了 config.yaml`，闸门无法确认磁盘上真读了。
  它查的是**记录内部的一致性**——但这恰恰是"忘了"的暴露面：忘了的链在记录上接不上。
- **不判语义对错。** `edit` 改的内容对不对，闸门不管（那是 `selftest` / 人审的事）。
- **记录造假防不住，但造假比老实记更贵。** 要骗过闸门得编一条自洽的假链，
  而老实记一行只要 3 秒。设计目标是**让老实记成为阻力最小的路径**。
- **子 agent 的记录同样要核。** 汇总进来的 trace 也走同一道闸门——
  "子 agent 说做完了"本身就是声明（见 SKILL.md 第 [8] 步）。
